## 2. テストの考え方
- **取り出しテスト**: AI に「質問の中身」を決まった形（JSON）で返させ、正解と比べる。数値の計算はさせない
- 雑談の返事の質は測らない（雑談は後回し）。雑談の質問（#21〜#23）は、`chat` と**判別できるか**だけを見る
- 自分のパーティの機能も後回し。#18〜#20 は、`my_team` と**判別できるか**だけを見る
- ロトムの口調はテンプレートで出すので、AI の口調は測らない
- **連続テスト**: 1 分間に 5 問続けて送り、止まらないかを見る（要件 N2）
- 全候補に**同じ指示文・同じ質問**を使う。各質問を 3 回ずつ実行し、ぶれも見る
- 音声認識の聞き間違いを想定した質問（#27・#28）も入れる。音声認識そのものの比較は別の計画にする

## 3. 取り出す項目（JSON の形）
| 項目 | 内容 | 例 |
|---|---|---|
| `intent` | 質問の種類 | `damage` / `speed` / `type` / `stats` / `learnset` / `move_info` / `my_team` / `chat` / `clarify`（聞き返しが必要） |
| `attacker` / `defender` | ポケモン（英語名） | `Mimikyu` / `Garchomp` |
| `pokemon` | 単体の質問の対象 | `Gholdengo` |
| `move` | わざ（英語名） | `Play Rough` |
| `conditions` | 指定された条件 | 持ち物、特性、性格、SP（ステータスポイント。「252振り」と言われた場合は 32 とみなす）、ランク、天候、フィールド、メガシンカ、最速・最遅 など（側ごと） |
| `uses_context` | 直前の会話を使ったか | `true` / `false` |
| `missing` | 足りない情報 | `["defender"]` |
| `unknown_names` | 知らない名前 | `["アロロ"]` |

- 名前は日本語のまま返させ、英語名への変換はサーバ側の名前の解決で行う（構成設計 A5）

## 5. 評価の観点と合格ライン（案）
| 観点 | 測り方 | 合格ライン |
|---|---|---|
| 取り出しの正確さ | #1〜#17、#24〜#30 で、正解の要点が全部合っている割合 | 90% 以上 |
| 後回しの機能の判別 | #18〜#20 を `my_team`、#21〜#23 を `chat` と判別できた割合 | 6 問とも |
| 聞き返しの正しさ | #24〜#26 で、勝手に補わず clarify にした割合 | 3 問とも |
| 数値の捏造がない | 取り出しの出力に、ダメージや種族値などの数値を AI が書いていない | 0 件 |
| 速さ | 送ってから返答が届くまで（取り出し） | 中央値 1.5 秒以内、遅い方の 5% でも 3 秒以内 |
| 連続の質問 | 1 分間に 5 問送る（3 回） | 上限エラー 0 件 |
| ぶれ | 同じ質問 3 回の結果が一致する割合 | 90% 以上 |
| 費用 | 1 問あたりの実際の使用量から計算 | 月 1,000 問で $10 以内 |
| データの扱い | 各社の規約で、入力が学習・改善に使われるか | 記録のみ（判断材料） |

## 6. 決め方
1. 合格ラインを満たす候補の中から、**取り出し用**は「上限の大きさ → 速さ → 正確さ」の順で選ぶ（第一候補は Gemma）
2. どれも満たさない場合は、指示文の改善 → ルールで即答する範囲の拡大 → Gemini Flash をクレジットで使う、の順で検討する
3. 予備（使えないときの切り替え先）を、別の会社から 1 つ決めておく

## 7. 結果

### 7.1 第 1 回（2026-10-10）
- 仕組み: `eval/`（指示文 `prompt.ts`、質問と採点 `cases.ts`、実行 `run.ts`、集計 `summarize.ts`）。生の出力は `eval/results/*.json`、実行ログは `eval/logs/`
- 全候補に同じ指示文。30 問 × 3 回、temperature 0、JSON モード。思考（推論）は最小に設定
- #2・#3 は同じモデルなので、無料枠で精度を測るはずだったが、無料枠の上限で 16 問しか測れなかった（下記）。計画外で Gemini 3.5 Flash-Lite と Groq の gpt-oss-20b も測った（Groq の Qwen は時間の都合で取りやめ）

- 単価は比較サイトの値（公式ページはこの環境から開けなかった）。**採用前に公式ページで確認する**

### 7.2 上限（実測）
| 候補 | わかったこと |
|---|---|
| Gemma | 1 日の上限には当たらなかった（約 110 回）。**「Internal error」（HTTP 500）が本番 90 回中 10 回、連続テストで 15 回中 7 回**。どれも 0.15 秒ほどで返っており、受け付けの時点で断られている（混雑とみられる） |
| Gemini 3.8 Flash（無料枠） | **1 日約 20 回**で 429（1 日の上限）。対戦用には足りない。1 分あたりの上限にも時々当たった |
| Gemini 3.5 Flash-Lite | 1 分あたりの上限に時々当たる（本番で 429 が 12 回。待てば通る）。連続テスト（1 分 5 問）はエラーなし |
| Groq（gpt-oss） | API の応答ヘッダで **1 日 1,000 回・1 分 8,000 トークン**。この指示文だと 1 分 7 問ほどで、それ以上は数秒待たされる。1 分 5 問ならエラーなし |

### 7.3 間違いの傾向（全候補共通）
- **聞き返しが弱い**: #25「ミミッキュのじゃれつく」（相手がいない）を move_info などにしてしまう。#26「アロロ」（存在しない名前）は、unknown_names に入れても計算に進む、または「アローラロコン」などに勝手に置き換える
- **#17「じゃれつくって何タイプ？」を type にする**（正解は move_info）。指示文の「タイプは type」に引っぱられている
- gpt-oss は攻撃側と防御側の取り違え（#1・#9）、聞き間違いの補正（#27・#28）が苦手
- 数値の捏造は全候補 0 件

### 7.4 結論（第 1 回）と次の手
- 合格ラインを全部満たす候補はない。6 章の手順どおり、**次は指示文の改善**（聞き返しの条件を明確にする、「何タイプ？」の例を足す）をして、Gemma と Flash-Lite で測り直す
- 取り出しの第一候補だった Gemma は、正確さとぶれは最もよいが、速さ（中央値 2.45 秒）と 500 エラーが問題。要件 Q1（AI を使う質問は 2〜3 秒以内）なら速さは許容範囲だが、エラー時の切り替え先が必須
- 速さ・安定性では Flash-Lite が最もよい（計画外の候補なので、要件 5.2 に加えるかを決める）
- Gemini Flash（3.8）を測るには、上限が戻るのを待つか、クレジット（#3）を設定する必要がある
- 予備（別の会社）は Groq の gpt-oss-120b が候補だが、正確さが低い。指示文の改善後に測り直して決める
- データの扱い（入力が学習に使われるか）は、公式ページが開けず未確認
